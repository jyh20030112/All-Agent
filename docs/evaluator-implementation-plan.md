# Harness 评估器实现计划

状态：阶段 1～6 已实现。`ejagent.evaluation` 提供确定性检查、可选 `ModelJudge`、
正式 Streamlit 接入和独立的 `CompletionPolicy`。默认仍使用确定性评估与观察策略；
显式启用语义项目或完成拦截后才改变对应行为。实际接口和预算边界见
[评估模块使用指南](evaluation.md)。

## 1. 实现前的基础与缺口

以下保留规划时的起点，所列缺口现已由阶段 1～6 处理。

- `_trajectory/online.py` 已定义 `CheckpointEvaluator.evaluate()`，在线监控器可以调用它。
- `examples/streamlit_runtime.py` 已实现 `_ProbeCheckpointEvaluator`，但只验证三个探针需求。
- 现有分析器已负责覆盖率、进度和循环判断；正式评估器应复用这些能力。
- 当前请求只有检查点编号、信号和前一检查点，没有任务验收标准、当前产物或完成回复。
- 当前结果包含事实和需求／约束布尔值，但缺少逐项判断依据、采集失败与冲突的统一表示。
- 不完整、过期或未知事实会被现有 Context 投影拒绝，不能直接用于温和降级反馈。
- 完成建议目前只记录，不控制 Run 结束；评估器实现与完成策略实施应分别交付。

## 2. 首版目标

实现一个可组合的 `GoalEvaluator`，根据本次 Run 的验收标准和可追溯证据，输出每项需求、
约束的判断及理由。宿主提供标准、证据访问和必要的验证函数；评估器统一处理证据有效性、
判断归并、超时、去重及结果记录，再由适配器生成现有 `CheckpointEvaluation`。

确定性验证先交付；需要语义判断的项目再接入独立的模型评估模块。模型评估使用 `ModelPort`，
可以与 Actor 使用同一模型配置，但使用独立请求和评估指令。模型不同不等于判断一定可靠。

评估器不修改用户目标、不执行修复动作、不计算另一套覆盖率，也不直接终止或重启 Run。
通用指的是评估流程可复用；应用仍需提供领域证据和验收标准。

## 3. 输入与输出

### 任务标准

`EvaluationPlan` 包含稳定的 Goal、版本、有序 Requirement／Constraint，以及各项的描述、
验证方式和所需证据。首版允许宿主显式声明；没有标准的任意聊天任务不应默认获得完成分数。

模型从自然语言生成验收标准属于后续可选功能：结果是候选标准，不能擅自增加用户义务。
同一 Run 的标准版本固定，保证检查点覆盖率可比较。修改目标或标准时开启新 Run；
Follow-up 单独绑定标准，不能沿用上一次 Run 的可变闭包状态。

### 评估输入

输入需要关联 Run ID、标准版本、当前检查点、上一评估、当前环境版本和有界证据引用。
完成审核还要包含待返回的回复或产物引用；只检查环境状态不足以评价答案是否满足请求。

Harness 在接收 Run 时绑定标准。Kernel 提供工具批次与完成候选等执行事实；原始产物由
宿主证据读取器按引用提供。不依赖提交后的 `RunObserver` 为运行中的审核补数据。
新增传递类型必须保持稳定层不导入 `_trajectory` 或具体 evaluator 的依赖方向。

### 逐项结果

每项返回 `pass`、`fail`、`unknown` 或 `conflict`，并附标准 ID、证据引用、简短理由、
证据有效版本、所用验证方式及缺失证据。映射到现有轨迹接口时分别为 `True`、`False`、
`None`、`None`；冲突的具体信息保留在完整评估记录中。

`fail` 表示有有效证据证明条件未满足。采集超时、工具不可用或无法解析的模型输出应产生
`unknown`，不能冒充失败或成功。没有明确证据支持的模型判断不能成为当前环境事实。

## 4. 判断流程

1. 读取本次 Run 的固定标准和本检查点需要的证据。
2. 获取带来源、范围、版本和观察时间的证据，检查它是否仍有效。
3. 执行确定性验证，例如文件存在性、结构字段、测试结果或业务 API 状态。
4. 对显式声明为语义判断的项目，调用模型评估；只提供标准、有关证据和完成候选。
5. 校验返回的项目 ID、状态、引用和结构，保留冲突及缺失项。
6. 计算事实更新、失效和新证据，生成逐项报告并适配到轨迹检查点。

同一明确命题的有效确定性结果不能被模型自行推翻；证据范围不同则分别记录，不能把局部
测试通过当成整个需求通过。互相矛盾且无法消解的证据保留为冲突，不用平均分掩盖。

模型评估输出不要求完整思维过程，只需要可检查的理由与引用。产物和工具文本作为待评估
数据传入，其中的指令不能修改评估标准或授权额外动作。

## 5. 证据与轨迹的一致性

- 证据访问位置、采集记录与语义身份分开。重复采集同一事实，不应仅因时间戳或随机 ID
  不同就生成新的状态或“新证据”。现有事实比较包含证据引用，适配器必须保持引用稳定。
- `new_evidence` 可以表示减少不确定性的证据，不限于新增通过项；但重复读取同一内容
  不应阻止循环被检出。保留 Run 内已见证据身份与有效版本。
- 状态指纹基于标准版本和规范化的目标相关事实，不含模型理由、请求编号、累计成本等噪声。
- 文件内容或外部状态版本变化时，对依赖旧版本的验证结果显式失效，重新采集或返回未知。
- 尽可能在一致的环境快照上采集；读前后版本不同且无法获得稳定快照时，不确认状态等价。
- 验收标准和当前事实都需要可追溯依据；`fact_capture_complete` 根据必要采集是否成功设置，
  不能为了满足投影器约束强行置为 `True`。

## 6. 调度、成本与失败处理

沿用 baseline、整批工具完成和 completion proposed 三个自动采集时机。普通检查点仅刷新
受影响项目；复用结果必须满足依赖和版本仍有效。完成审核覆盖全部需求与约束，不能跳过
未验证项目；有效快照上的确定性结果可以复用。

模型评估单独设置超时、请求／Token 预算与并发限制，使用注入的取消令牌。记录评估成本
及 Actor 成本各自的明细，并提供可相加的总成本，避免隐藏额外开销或把验证误算成 Actor
动作。模型连接资源由 Harness 生命周期管理。

预期的临时不可用以逐项未知和诊断返回，不触发现有“监控异常后整次 Run 停止采集”的
处理。协议损坏等实现错误仍走明确的错误通道。

Context 需要增加有限反馈路径：事实不完整时仅说明评估不可用、缺少哪些证据、哪些旧结论
已经失效，不投影未经验证的事实，不把未知项伪装成当前真相。分析器继续保持证据不足的
判断。此路径与完整事实投影分别验证。

Run 结束、取消和异常时统一释放证据快照、评估缓存与暂存帧。评估记录引用应在约定保留期
内可解析；首版可用独立的 JSONL 评估日志及受控产物目录，Audit 记录关联 ID，不把整份
大产物写入 Conversation。基础 SessionStore schema 不因新增评估而被迫迁移。

## 7. 模块形状

建议实现放在 `src/ejagent/evaluation/`，区分类型、编排、确定性验证、可选语义判断和轨迹
适配。对宿主保留标准配置、证据读取与单次评估等少量必要接口；缓存、归并、序列化和
调度策略留在模块内部。语义判断使用现有 `ModelPort`，不再建立第二套模型调用体系。

首版复用内部轨迹类型，通过适配器接入现有监控器，不同时承诺整个 `_trajectory` 成为
稳定 API。用两个实际领域验证接口后，再决定需要迁移到 `contracts/` 的共享类型。

## 8. 分批交付

| 阶段 | 交付内容 | 验收条件 |
| --- | --- | --- |
| 1. 标准与输入 | 任务标准、逐项结果、Run 绑定及完成候选传递 | 普通 Run、Follow-up、取消互不串数据；缺标准不产生虚假分数 |
| 2. 确定性实现 | 证据读取、验证函数、事实与结果适配 | 探针与文件产物两类场景复用同一评估流程 |
| 3. 正确降级 | 证据失效、未知／冲突、有限 Context 反馈、生命周期清理 | 无证据不算通过；采集失败后可在后续检查点恢复 |
| 4. 可选模型判断 | 显式语义项目、结构输出、引用校验、预算 | 无效输出或引用变为未知；模型不能覆盖有效的确定性失败 |
| 5. Harness 示例 | 使用正式评估模块，展示逐项依据、来源、成本和缺失项 | 模型请求收到真实反馈；关闭评估保留原有行为 |
| 6. 独立后续策略 | 讨论并实现完成审核是否拦截、何时继续 | 依据误报、成本及可用性证据单独决定，不隐含在评估器中 |

首个可用版本以阶段 1～3 为里程碑；阶段 4～5 在同一接口上扩展。不要等模型判断完成后
才验证确定性路径，也不要用 Probe 的固定三个布尔值冒充通用任务评估。

## 9. 关键回归场景

- Agent 宣称完成，但所需文件不存在：对应项失败。
- 文件存在但内容不满足标准：结构验证失败，或语义项未通过。
- 验证器超时、证据损坏、模型返回未知项目 ID：结果未知并保留诊断。
- 刚通过的验证依赖文件随后变化：旧证据失效，不能继续沿用通过状态。
- 每轮重复读取相同事实：不产生伪造的新证据，循环判断仍可成立。
- 需求增加满足但约束被破坏：复用现有分析器识别退步。
- 并发工具批次与外部状态变化：不会把不一致快照当成可确认状态。
- 有限反馈不携带过期事实，且不会因缺证据直接破坏普通 Run。
- 用户取消、排队 Follow-up、会话恢复：标准、证据和反馈的 Run 归属正确。
- 模型评估超过预算：停止该评估调用，保留已验证结果及未知项，成本可核对。
- 完成建议不通过：在尚未开启执行策略时仍保留当前终止语义，避免悄悄改变行为。

## 10. 本次落地选择

首版领域保持探针与文件产物；标准由宿主显式声明，模型不会自动生成或修改标准。
语义判断仅处理 `semantic=True` 项目，完成时才有意义的项目声明 `completion_only=True`。
可设置确定性前置检查，失败、未知或冲突时不调用模型改判。

完成策略默认观察；宿主可启用 `ENFORCE`，在当前 Run 内接收反馈并重试，达到上限则失败。
这避免将模型评估的误判或证据服务不可用直接变成默认阻断。语义模型的实际误报率仍需
由应用基于真实任务校准，回归测试证明的是协议、证据、预算和控制行为。

模型总 Token 预算按 Provider 实际回报核算，单次在途调用可能超过余额。超额结果返回未知、
保留实际成本并停止后续请求；未回报用量同样禁止继续调用。这不是硬性预付费额度。
输出上限、请求次数、字节限制、超时和并发限制另外执行。取消时保留中断报告和未知用量。

验收覆盖 `tests/test_evaluation.py`、`tests/test_semantic_evaluation.py` 和
`tests/test_streamlit_example.py`；Provider 适配测试验证输出上限传递，安装包 smoke test
验证公开导出。Streamlit 展示逐项依据与 Actor／Judge 成本，并持久化完整评估日志。
